The bug was in xarray's `xr.where` function at `xarray/core/computation.py:1832`, where passing a scalar value for the `x` parameter (the second argument to `where`) caused an IndexError when `keep_attrs` was set to `True` via `xr.set_options(keep_attrs=True)`. The symptom was a crash on `attrs[1]` — an index-out-of-bounds error on the attrs list. The user-facing behavior was that `xr.where(xr.DataArray([1, 2, 3]) > 0, 1, 0)` would fail under `keep_attrs=True` because the scalar `1` has no `.attrs`.

The root cause lay in how `keep_attrs` was resolved around line 1827–1832 of `computation.py`. When the user-level option `keep_attrs` resolved to `True` via `_get_keep_attrs(default=False)` at line 1827, the code constructed a lambda `keep_attrs = lambda attrs, context: attrs[1]` at line 1832 to grab the attributes of `x`, the second parameter, matching the behavior of `DataArray.where`. However, `apply_ufunc` — which eventually calls this lambda — builds the `attrs` list by filtering arguments to only those that are xarray objects (DataArray or Dataset). When `x` is a plain scalar like `1`, it gets excluded from that list entirely, so `attrs` might contain only one element (the condition's attrs at index 0) or even be empty, making `attrs[1]` crash.

The fix replaced `lambda attrs, context: attrs[1]` with `lambda attrs, context: getattr(x, "attrs", {})`. Since `x` is already in scope as a closure variable from the enclosing `where` function, this directly accesses its attributes without relying on the filtered attrs list that `apply_ufunc` constructs. For scalars, `getattr` returns an empty dict, which is the correct behavior — scalars carry no metadata. For DataArray inputs, it returns the actual attrs dict. This approach was preferred over alternatives like trying to fix the indexing logic or adjusting how `apply_ufunc` builds its attrs list, because the closure-based access is simple, robust, and doesn't require changes to the more complex `apply_ufunc` internals. The `merge_attrs` function in `xarray/core/merge.py` consumes the return value downstream when `keep_attrs` is a callable, so the fix's return type (a dict) is compatible. The key non-obvious discovery was that `apply_ufunc` silently strips non-xarray arguments before building the attrs list passed to the `keep_attrs` callable, meaning positional assumptions about which index corresponds to which original argument break whenever any original argument is a scalar or non-xarray type.
