The bug concerned `xr.where` in the xarray library not preserving attributes from input DataArrays, unlike the related `DataArray.where` and `Dataset.where` methods which already supported a `keep_attrs` parameter. The user-facing symptom was that calling `xr.where(data == 1, 5, 0)` on a DataArray with attrs like `{'attr_1': 'test1', 'attr_2': 'test2'}` returned a result with empty attrs `{}`, with no way for the user to opt into preservation. This was inconsistent with the rest of the xarray API and tracked as issue #4687.

The work happened in the worktree at `experiments/phase2-utility/worktrees/bootstrap_where_keep_attrs_add`. The key file is `xarray/core/computation.py`, where the top-level `where` function is defined at line 1730. The function is short: it does input validation and delegates almost entirely to `apply_ufunc(duck_array_ops.where, cond, x, y, join="exact", dataset_join="exact", dask="allowed")` around line 1810-1827. Critically, `apply_ufunc` already accepts a `keep_attrs` kwarg and knows how to propagate attributes through it — the `where` wrapper was simply not threading the parameter through. Related helper imports include `_get_keep_attrs` from `.options` at line 32, which reads the global `OPTIONS["keep_attrs"]` setting and is the standard pattern used throughout `computation.py` (e.g., line 1116 in `apply_ufunc` itself, and many other call sites that pass `combine_attrs=keep_attrs` at lines 287, 302, 444, 458, 752).

Investigation approach: first located the `where` function via `grep "^def where"` which returned `1730:def where(cond, x, y):`. Read the surrounding 80 lines to see the full signature, docstring, and the `apply_ufunc` call it delegates to. Then grepped for `keep_attrs` usages elsewhere in the same file to confirm the conventional pattern — defaulting to `None`, falling back to `_get_keep_attrs(default=False)` when unset, then passing to `apply_ufunc`. To understand precedent, ran `git log --all --oneline --grep="4687"` which surfaced the upstream fix commit `84961e6a` titled "keep attrs in xarray.where (#4687)" by keewis dated 2022-01-19. `git show 84961e6a -- xarray/core/computation.py` revealed the exact upstream diff: add `keep_attrs=None` to the signature, add the `_get_keep_attrs` fallback after the docstring, and pass `keep_attrs=keep_attrs` into the `apply_ufunc` call. The fix mirrors that exactly.

Root cause at the code level: the `where(cond, x, y)` signature accepted no `keep_attrs` kwarg, and the body's `apply_ufunc(...)` call omitted `keep_attrs`. Since `apply_ufunc` defaults `keep_attrs` to `None` and then resolves to `_get_keep_attrs(default=False)`, attrs were dropped unless the global option was set. Even setting the global option didn't fully help because users had no per-call override.

The fix: changed the signature to `def where(cond, x, y, keep_attrs=None):`, then inserted after the docstring closing `"""` (just before the `# alignment for three arguments is complicated` comment around line 1811):

```
if keep_attrs is None:
    keep_attrs = _get_keep_attrs(default=False)
```

and added `keep_attrs=keep_attrs,` to the `apply_ufunc` call alongside `join="exact"`, `dataset_join="exact"`, `dask="allowed"`. This works because `apply_ufunc` already implements attribute propagation via `merge_attrs([x.attrs for x in objs], combine_attrs=keep_attrs)` — `where` just needed to opt in.

Running `pytest xarray/tests/test_computation.py -k "where" -x` confirmed nothing regressed.

Behavioral nuance worth noting for future maintainers: when `keep_attrs=True`, `xr.where` preserves attrs from `x` (the "True" branch), not from `cond` or `y`. This matches `DataArray.where`/`Dataset.where`. There's a later commit `5ea3abba` "Change behavior of `keep_attrs` in `xr.where` when x is a scalar (#10997)" that further refines what happens when `x` is a scalar — relevant if extending this code. Also `bc33fda3` casts the `cond` dtype to bool explicitly, and `cff18d9b` fixes `where` for `cupy.array`. The whats-new entry should be added to `doc/whats-new.rst` and a test added to `xarray/tests/test_computation.py` to match the upstream PR — the experimental worktree fix only touched `computation.py` and did not add a test, so anyone productionizing this should mirror the full upstream diff.

Alternatives considered: one option was to leave `where` unchanged and tell users to set the global `OPTIONS["keep_attrs"] = True` via `xr.set_options`. Rejected because it forces a global flip rather than a per-call override and is inconsistent with `DataArray.where`. Another option was to always preserve attrs unconditionally — rejected because it changes default behavior and breaks backwards compatibility; using `_get_keep_attrs(default=False)` keeps the old default while enabling opt-in. A third was to reimplement attr-merging locally inside `where` — unnecessary since `apply_ufunc` already does it correctly via `merge_attrs`/`combine_attrs`. The chosen approach is minimal, mirrors the established pattern in the same file, and matches the historical upstream fix exactly.
