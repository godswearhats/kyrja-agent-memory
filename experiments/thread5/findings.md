## Original Research Question

Does retrieval quality affect downstream task performance? Specifically: do the same memories produce better answers when retrieved with better methods? (The "ceiling effect" hypothesis.)

## Method

### Literature Survey

Reviewed four papers on RL-trained memory construction:

- **Mem-alpha** (2509.25911): GRPO-trained 4B model beats GPT-4.1-mini on memory construction. Uses BM25 retrieval only. Never ablates retrieval quality.
- **MemBuilder** (2601.05488): ADRPO with attributed dense rewards. 4B model beats Claude 4.5 Sonnet on LoCoMo. Uses text-embedding-3-small. Never examines retrieval quality.
- **BudgetMem** (2602.06025): RL-trained query-aware budget-tier router. Uses Contriever top-5. Fixed retrieval across all conditions.
- **GAM** (2511.18423): JIT memory with dual memorizer/researcher agents. Key finding: researcher (retrieval) capacity is far more sensitive to model size than memorizer (encoding) capacity — even a 0.5B memorizer is competitive, but a weak researcher collapses the system.

**Central gap identified:** Every paper treats retrieval as a fixed, unexamined constant. Nobody has studied what happens when you improve retrieval quality while holding encoding constant, or vice versa.

### Ceiling Effect Experiment

**Hypothesis (H2):** The downstream performance ceiling of any encoding strategy is bounded by retrieval quality. Improving retrieval raises this ceiling even without retraining the encoder.

**Data:** 2,920 tool-call chains extracted from 804 real Claude Code sessions. Each chain encoded with intent+outcome strategy (from Thread 1) via Haiku. Synthetic retrieval query generated per chain via Haiku. Ground truth answers generated from full chain context via gemma3:12b.

**Retrieval tiers (same 2,920 memories, different search methods):**

| Tier | Method |
|------|--------|
| T0 | No memory (question only) |
| T1 | BM25 keyword matching |
| T2 | Semantic embedding (nomic-embed-text) |
| T3 | Hybrid BM25 + embedding with RRF fusion |

**Evaluation:** Top-3 memories retrieved per query. Haiku answers the question given retrieved memories. Scored two ways: F1 token overlap and LLM-as-judge (Haiku, CORRECT/PARTIAL/WRONG).

**Scale:** 2,920 queries × 4 tiers = 11,680 QA evaluations + 11,680 judge evaluations.

## Key Findings

### 1. Memory helps, but retrieval method barely matters

Going from no memory to any retrieval gives a +54% F1 improvement (p=1.000). But BM25, semantic, and hybrid all perform within 1.5% of each other. The retrieval quality ladder effectively plateaus at keyword matching for this encoding strategy and pool size.

### 2. The binding constraint is encoding quality, not retrieval quality

The LLM-as-judge reveals that 98% of answers are factually wrong across ALL tiers — even when the correct memory is retrieved. Intent+outcome encodings compress tool-call chains (~3,000 tokens average) down to ~60 tokens. The details needed to answer specific questions (file paths, function names, error messages, exact commands) are discarded during encoding.

This means improving retrieval cannot overcome encoding information loss. Even perfect retrieval (100% hit rate) would still yield ~98% wrong answers because the memories themselves don't contain enough detail.

### 3. The ceiling effect hypothesis was correct — but the ceiling is encoding, not retrieval

The original hypothesis asked: does retrieval quality bound performance? The answer is: not at this scale and encoding quality. The actual bound is encoding information loss. Retrieval improvements add marginal value because the memories are too compressed to be useful regardless of how well you find them.

### 4. This specifically affects agentic (tool-call) memory, not all memory types

Intent+outcome encoding compresses inherently high-dimensional data. A 10-step tool chain touches files, produces errors, makes decisions, and creates commits. Summarizing that in 60 tokens is extremely lossy.

Conversational memory — preferences, facts, decisions — is naturally more compact. Prompted extraction (Mem0-style) handles it well because the source information is already close to its compressed form. The encoding quality problem is specific to agentic work.

### 5. RL-trained encoding is likely essential for agentic memory

No hand-crafted encoding strategy can anticipate what details a future query will need. Sometimes the file path matters. Sometimes the error message. Sometimes the decision rationale. Prompted encoders guess. RL-trained encoders learn what to keep based on actual downstream QA accuracy.

This reframes RL-trained encoding from "research opportunity" to "likely prerequisite for agentic memory to work." Competitors who only handle conversational memory can get by with prompted extraction. Kyrja's differentiator — encoding tool-call chains — requires RL to overcome the information loss ceiling.

## Implications for Kyrja

**Encoding quality is the critical path, not retrieval quality.** The MVP's retrieval stack (BM25 + vector with RRF fusion) is sufficient. Investing further in retrieval infrastructure before solving encoding would yield diminishing returns.

**RL-trained encoding should move up in priority.** Thread 5 was originally framed as "high strategic value, high cost." The data now suggests it may be essential for the agentic memory use case to work at all. The 98% information loss rate with prompted encoding is a product-quality problem, not just a research opportunity.

**The encoding-retrieval co-evolution thesis is strengthened, not weakened.** While we didn't see a retrieval ceiling effect, we discovered something more important: encoding and retrieval are sequentially dependent. You need encoding that preserves relevant detail first, then retrieval quality determines how efficiently you find it at scale. An RL-trained encoder that co-adapts with the retrieval system is the path to both.

**Memory type segmentation is validated.** Different memory types (conversational vs agentic) need different encoding strategies. This supports the pluggable encoder architecture in the MVP spec.

## Known Limitations

- **Synthetic queries have high lexical overlap with source chains.** Real queries would be harder for BM25, potentially widening the retrieval tier gap.
- **F1 token overlap is biased toward keyword-matching approaches.** The LLM-as-judge partially corrects this but shows the deeper encoding problem.
- **Single encoding strategy tested.** Intent+outcome may not be representative of all prompted encoding approaches. Mem0-style extract-all or richer formats might perform differently.
- **Ground truth generated by gemma3:12b**, a weaker model. Reference answers may themselves be imperfect.
- **Pool is single-domain** (skewed toward game development). Enterprise cross-domain queries might show different retrieval tier dynamics.

## What's Next

1. **Test richer encoding strategies.** Before concluding that prompted encoding can't work for agentic memory, test more detailed formats — full entity extraction, state-diff encoding, or a "key facts" approach that preserves specific details alongside intent+outcome.
2. **Human-written queries.** The synthetic query limitation applies to both Thread 1 and Thread 5. Real queries would be a stronger test of retrieval tier differentiation.
3. **RL training feasibility.** Scope what minimal RL infrastructure would be needed to train an encoder on this data. Mem-alpha used 32 H100s for 3 days — can we find a cheaper path?
4. **Encoding budget experiments.** What happens at 200 tokens per memory instead of 60? 500? Where does the information loss curve flatten?
